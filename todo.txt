- build 52 device checks.  Build 52 is a data-loss fix that nothing on a Mac can

  sandbox.  Everything below was verified on the host (48 checks, and a
  before/after against real FileManager calls) but not on a device.  On the
  first TestFlight build, in this order, with a THROWAWAY disk library:
    1. W8 ANYFILE.TXT ..    -> refuses or exports to Exports/export.txt.
       Documents, Disks, Imports must all still be there afterwards.  This is
       the one that used to delete everything.
    2. W8 FOO.TXT           -> still exports normally.  The H_CAPS interlock in
       the new w8.com must NOT fire for a path-less export; if it does, a

    3. W8 FOO.TXT out.txt   -> lands in Exports as out.txt, and the "To host:"
       line names the real Exports path rather than a bare name.
    4. R8 NOSUCH.COM        -> reports "not found in Imports".  Before build 52
       it silently loaded the first file in the folder instead.
    5. R8 FOO.COM where the file is really foo.com -> still found (case).
  Note 1 and 2 need a disk image carrying the NEW w8.com, which the catalog does
  not serve yet - copy one in through Files from romwbw_emu/disks/.

- BLOCKING A RELEASE, and the reason build 52 exists: do not bump releaseTag
  (grep releaseTag in EmulatorViewModel.swift, still v1.4.5) until build 52 or
  later is what users are running.  Refreshing the disk-image catalog is what
  puts a path-capable W8 in front of everyone, and before 52 that W8 could
  delete the whole Documents folder.  The cross-repo order is romwbw_emu's
  docs/RELEASE_ORDER_2026-08-25.md - this port is step 1, the catalog bump is
  step 5, and the one thing that must never happen is refreshed images being
  attached to the EXISTING v1.4.5 tag, which would reach every installed app
  with no update at all.  Read the next item before walking that order: the
  catalog bump destroys user data by a second route that has nothing to do with
  W8, and it fires whether or not build 52 has shipped.

- THE SECOND DATA-LOSS PATH ON THAT SAME RELEASE STEP.  disks.xml carries a
  version attribute of its own (<disks version="12"> at the pinned v1.4.5, 13 in
  release_assets/ today, and it has moved on essentially every catalog change -
  1, 2, 6, 7, 8, 9, 10, 11, 12, 13).  On every successful
  catalog fetch, checkCatalogVersionAndInvalidate (EmulatorViewModel.swift)
  compares that attribute against the stored "catalogVersion" default and, on
  any difference, calls deleteAllDownloadedDisks() before showing the user an
  alert saying it has happened.  So step 5 does not merely put a new W8 in front
  of users, it wipes disks on their devices, unprompted, on the next launch.
  Two things make it worse than "the downloaded disks come back":
    - deleteAllDownloadedDisks() loops over `contents where url.pathExtension ==
      "img"` in Documents/Disks, so it also deletes disks the user imported
      through Files and disks the app itself made with createNewDisk.  Neither
      is in the catalog and neither can be re-downloaded.  Those are gone.
    - a downloaded disk is writable and is exactly where a user's CP/M work
      lives, which is the point KNOWN_PROBLEMS.md makes under "Data Loss Risk
      with GitHub Disks" - except that entry describes the trigger as a new disk
      being released and downloaded over the old one, and the real trigger is
      broader and needs no download and no tap at all.  That entry now carries
      the real trigger and points back here.
  Where this was and was not written down before, since the answer is not
  "nowhere": not in this list, not in the CHANGELOG, and not in
  RELEASE_ORDER_2026-08-25.md, which reasons only about W8 and R8.  But it WAS
  in docs/DISK_DISTRIBUTION.md's "Version Attribute" section, described wrongly
  and softly enough to read as harmless - downloaded disks "may be invalidated
  if checksums changed", users "are notified of available updates".  Every
  clause of that was false: no checksum is consulted, the deletion is
  unconditional on any attribute difference, it is not limited to catalog disks,
  and the user is told after the fact rather than offered an update.  That
  section now describes the code and points here.
  Not fixed here because the fix is a user-facing decision rather than a patch:
  copy-on-write on first guest write, or confirm before wiping, or spare
  anything the catalog does not name, or keep the wipe and give the user an
  export path first.  Whichever it is, it has to be in the same binary as the
  catalog bump, for exactly the reason build 52 has to be.

- two more that have sat in KNOWN_PROBLEMS.md and have never been in this list.
  Both verified still true against the source, both far smaller than the one
  above.  New disks are always 8 MB: createNewDisk(at:size:) takes a size:, the
  single call site in ContentView passes none, and there is no size picker,
  while an imported disk is accepted up to maxDiskSize (64 MB).  And a created
  disk is Data(repeating: 0xE5, ...) and nothing else - no HD1K filesystem is
  laid down - so it is not usable until something formats it, which is what the
  cpmtools recipe in KNOWN_PROBLEMS.md is a workaround for.

- found while checking the above, not previously recorded: nothing verifies a
  downloaded disk's SHA256.  There are two download implementations in
  EmulatorViewModel.  downloadDiskWithRetry() does verify - it hashes the file,
  deletes it and retries on a mismatch - but its only callers are its own four
  retry arms, so nothing outside it ever reaches it.  Every real download goes
  through downloadDiskFromSettings() - both downloadDisk() and
  downloadDiskWithCompletion() call it - and that one moves the temp file into
  place without hashing it at all.  The catalog's sha256 survives only as the
  coloured text in DiskDownloadRow, computed after the file is installed and
  acted on by nobody.  Disk images are downloaded content that the guest then
  executes, so this matters most on exactly the release step above.  Either
  delete the dead path or move its check into the live one; the second is the
  point of having the hash in disks.xml at all.  docs/DISK_DISTRIBUTION.md
  asserted the opposite in three places - "SHA256 checksum is verified", "All
  downloads are verified against the manifest's SHA256 checksum", "No disk is
  used without passing verification".  Its "Integrity Verification" section is
  now labelled intended-not-shipped and describes the live path; whichever way
  this item is closed, that label comes off.

- a zero-byte W8 export produces no file on this port.
  emu_host_file_close_write() (emu_io_ios.mm) goes straight to IDLE when the
  buffer is empty rather than to WRITE_READY, and emu_host_file_get_write_data()
  returns nullptr for an empty buffer so checkHostFileState's guard bails out.
  An empty CP/M file is a real file and the CLI and Windows backends both create
  it; romwbw_emu fixed the identical thing in its browser backend in v1.36.
  Left out of build 52 deliberately - that build is a security fix and was kept
  minimal - so it is a divergence to close next, not a mystery.

- Ctrl+Left / Ctrl+Right / Ctrl+Up / Ctrl+Down still emit the same bytes as the

  tests only for .command, so the modifier is discarded before the Ctrl fold
  below it can see it, and neither SpecialKey nor KeyMap has a slot for a
  modified variant. Both siblings bind them now, to different bytes: cpmemu's
  Windows console sends ^A ^F ^W ^Z for word motion (extended_keys,
  src/os/windows/platform.cc:123-126, commit 0b8dc2b), and z80cpmw sends the

  conventions rather than an implementation. KNOWN_PROBLEMS.md said z80cpmw did
  the same thing ioscpm does and had no equivalent; both were stale and are
  corrected there now, without picking a convention. iPadOS only; macOS takes
  Ctrl+arrow at WindowServer.

- the terminal's remaining divergence from a strict VT: the erase family (ED,

  SGR background - EL at EmulatorViewModel.swift:2269, :2273 and :2277, ICH at
  :2341, DCH at :2355, ECH at :2367, and ED, which has no inline site of its own
  because all three of its arms delegate, at clearFromCursor/clearToCursor
  :2527-2552 and clearTerminal() :1340-1351. The neighbouring finals that fill a
  whole line - DL :2300, IL :2319, SD :2397 - blank with a default cell for the
  same reason and belong in the same sweep. A strict VT paints it. Changing
  that is a decision for the whole family at once - doing it to half would be

  VT - z80cpmw split those two apart for the same reason.
