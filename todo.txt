- THE SECOND DATA-LOSS PATH ON THAT SAME RELEASE STEP.  disks.xml carries a
  version attribute of its own.  It is at 13 both in release_assets/ and on the
  pinned v1.4.5 release (checked 2026-08-26 - an earlier version of this entry
  said the published one was 12, and it is not; the two agree byte for byte).
  It has moved on essentially every catalog change - 1, 2, 6, 7, 8, 9, 10, 11,
  12, 13.  On every successful catalog fetch, checkCatalogVersionAndInvalidate
  (EmulatorViewModel.swift) compares that attribute against the stored
  "catalogVersion" default and, on any difference, calls
  deleteAllDownloadedDisks() before showing the user an alert saying it has
  happened.  So step 5 does not merely put a new W8 in front of users, it wipes
  disks on their devices, unprompted, on the next launch.
  That the two 13s agree is not reassurance, it is the shape of the trap: there
  is nothing to fire today, and the very next catalog respin - which is step 4,
  and which the runbook tells you to bump the attribute for - fires it on every
  installed device at once.  It has also already fired once in the field, which
  nothing here recorded.  The 12 -> 13 bump reached users on 2026-07-22, when
  disks.xml was uploaded to v1.4.11 (asset timestamp 2026-07-22T10:41:09Z).
  v1.4.11 is Latest, and the app still floated on releases/latest then - the pin
  landed three days later, in 4be8a13 / build 42 - so every installed client
  holding 12 fetched 13 and wiped its Disks folder.  What that cost is not
  recoverable from here; the alert is all the user got.  (v1.4.5 was published
  2026-07-25 carrying the same bytes, so the pin itself changed nothing.)

- emu_host_file_get_read_name() answers "", and could answer truthfully.  It is
  newly defined here only because the v1.36 core made it a required backend
  symbol (see CHANGELOG.md); "" is a legal answer that emu_io.h explicitly
  allows, and it makes R8 print what the user asked for rather than what was
  really opened.  This port can do better, and the difference is visible: the
  Swift layer resolves the guest's leaf against Imports case-insensitively, so
  R8 FOO.COM that really opened foo.com currently reports FOO.COM.  The reason
  it was not done is that the resolved name never crosses back into the backend:
  emu_host_file_load() (the extern "C" entry point Swift calls) carries bytes
  and no name.  The shape of the fix is a named variant of that entry point -
  emu_host_file_load_named(const char* path, const uint8_t*, size_t) - storing
  the path in a g_host_read_filename that get_read_name() returns while
  HOST_FILE_READING, exactly as the write side already does with
  g_host_write_filename.  Small, but it is Swift plus Objective-C++ and nothing
  here can compile either.  The browser backend answers "" for the same reason
  and has the same item open.

- the terminal's remaining divergence from a strict VT: the erase family (ED,
  EL, ICH, DCH, ECH) blanks with a default cell rather than painting the current
  SGR background. Every site is a `TerminalCell()` with no argument, and the
  ones in this family are reachable from the case comments in executeCSI - EL
  under `case 0x4B: // 'K' - Erase in Line` (three arms), ICH under `case 0x40:
  // '@'`, DCH under `case 0x50: // 'P'`, ECH under `case 0x58: // 'X'` - and ED,
  which has no inline site of its own because all three of its arms delegate, in
  clearFromCursor() / clearToCursor() and clearTerminal(). The neighbouring
  finals that fill a whole line - DL `case 0x4D: // 'M'`, IL `case 0x4C: // 'L'`,
  SD `case 0x54: // 'T'` - blank with a default cell for the same reason and
  belong in the same sweep. (The line numbers this entry used to carry, :2269
  through :2397, were all 29 lines stale; grep the case comments instead.) A
  strict VT paints it. Changing that is a decision for the whole family at once -
  doing it to half would be worse than the current consistent-but-wrong
  behaviour. z80cpmw has since made exactly this change on its side, so the
  convention question is settled and only the work is left; none of it is shared
  code, so this port has to do its own. While in there: clearTerminal() is the
  ESC[2J path and resets scrollTop/scrollBottom, which erase-in-display does not
  do on a real VT - z80cpmw split those two apart for the same reason.
