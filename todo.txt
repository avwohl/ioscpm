- BLOCKING A RELEASE, and the reason build 52 exists: do not bump releaseTag
  (EmulatorViewModel.swift:128, still v1.4.5) until build 52 or later is what
  users are running.  Refreshing the disk-image catalog is what puts a
  path-capable W8 in front of everyone, and before 52 that W8 could delete the
  whole Documents folder.  The cross-repo order is romwbw_emu's
  docs/RELEASE_ORDER_2026-08-25.md - this port is step 1, the catalog bump is
  step 5, and the one thing that must never happen is refreshed images being
  attached to the EXISTING v1.4.5 tag, which would reach every installed app
  with no update at all.

- a zero-byte W8 export produces no file on this port.
  emu_host_file_close_write() (emu_io_ios.mm) goes straight to IDLE when the
  buffer is empty rather than to WRITE_READY, and emu_host_file_get_write_data()
  returns nullptr for an empty buffer so checkHostFileState's guard bails out.
  An empty CP/M file is a real file and the CLI and Windows backends both create
  it; romwbw_emu fixed the identical thing in its browser backend in v1.36.
  Left out of build 52 deliberately - that build is a security fix and was kept
  minimal - so it is a divergence to close next, not a mystery.

- Ctrl+Left / Ctrl+Right / Ctrl+Up / Ctrl+Down still emit the same bytes as the
  plain arrows. The nav-key branch in pressesBegan (TerminalView.swift:594)
  tests only for .command, so the modifier is discarded before the Ctrl fold
  below it can see it, and neither SpecialKey nor KeyMap has a slot for a
  modified variant. Both siblings bind them now, to different bytes: cpmemu's
  Windows console sends ^A ^F ^W ^Z for word motion (extended_keys,
  src/os/windows/platform.cc:123-126, commit 0b8dc2b), and z80cpmw sends the
  xterm modified forms \E[1;5A..D out of a modifier-aware key map
  (Keymap.h:164-167). Small, and it needs the choice between those two
  conventions rather than an implementation - written up in KNOWN_PROBLEMS.md,
  which still says z80cpmw has no equivalent and wants correcting whichever way
  the decision goes. iPadOS only; macOS takes Ctrl+arrow at WindowServer.

- the terminal's remaining divergence from a strict VT: the erase family (ED,
  EL, ICH, DCH, ECH) blanks with a default cell rather than painting the current
  SGR background - EL at EmulatorViewModel.swift:2269, :2273 and :2277, ICH at
  :2341, DCH at :2355, ECH at :2367, and ED, which has no inline site of its own
  because all three of its arms delegate, at clearFromCursor/clearToCursor
  :2527-2552 and clearTerminal() :1340-1351. The neighbouring finals that fill a
  whole line - DL :2300, IL :2319, SD :2397 - blank with a default cell for the
  same reason and belong in the same sweep. A strict VT paints it. Changing
  that is a decision for the whole family at once - doing it to half would be
  worse than the current consistent-but-wrong behaviour. z80cpmw has since made
  exactly this change on its side, so the convention question is settled and
  only the work is left; none of it is shared code, so this port has to do its
  own. While in there: clearTerminal() (:1340-1351) is the ESC[2J path and
  resets scrollTop/scrollBottom, which erase-in-display does not do on a real
  VT - z80cpmw split those two apart for the same reason.
