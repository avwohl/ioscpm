- [RELEASE] docs/ROM_ATTESTATION.md no longer describes a ROM in the bundle,
because there is no longer a ROM in the bundle.  It was rewritten on 2026-09-05
to cover the downloads alongside the bundled file, and rewritten again for build
66 to cover the downloads alone: it opens "This application contains no ROM of
its own", it carries a "What changed since the previous filing" section saying
that the 512 KB emu_avw.rom was removed and that the version the Store serves
today still contains it, and it lists the four published files with the size and
SHA-256 the catalog serves for each - fetched from the live catalog on
2026-09-08, which is the date on the document.  The corresponding-source URL
points at romwbw_disks, which holds src/emu_hbios.asm, the build scripts and the
SHA-256 pins for each upstream RomWBW package.  The document is correct as of
build 66; what it is NOT is submitted.  It is an attestation to Apple, so a
person has to read it, agree that it says what they are willing to affirm, and
attach it to the next review.  Nothing here can do that step.
  Worth a second read before it goes: the claim that changed is not a licence
claim - every ROM is the same GPLv3 material from the same two authors, bundled
or downloaded - it is that "included with the application" is no longer any part
of how a ROM reaches a device, and an attestation has to be true of the binary it
accompanies rather than of the one users are running today.

- [MAC] A local disk opened from Files is mounted with no release check at all.
  loadLocalDisk, reached from openLocalDisk and handleOpenDiskResult, takes
  whatever the picker returns and mounts it; nothing on that path consults
  romwbwVersion or CatalogMigration.versionedParts.  Info.plist carries
  UIFileSharingEnabled and LSSupportsOpeningDocumentsInPlace, both true, so
  putting a hd1k_*-v0-3.5.1.img into Documents/Disks on a 3.6.0 device is an
  ordinary thing a user can do, and it then boots in silence.
    The catalog path is NOT this.  Slots are release-scoped through
  CatalogMigration.versionedKey, and refreshAvailableDisks drops another
  release's catalog image through CatalogMigration.belongsToAnotherRelease - so a
  catalog disk shows as an empty drive rather than a wrong one.  Two gaps in that
  guard, both read rather than run: belongsToAnotherRelease only fires for a stem
  in knownCatalogStems, which is OBSERVED and grown by recordCatalogStems alone,
  so a stem this device has never fetched a catalog for is not recognised as
  another release's; and loadLocalDisk bypasses the guard entirely, known stem or
  not.
    z80cpmw filed the same family of bug on 2026-09-17 after MEASURING a machine
  that had 3.6.0 stored against two -v0-3.5.1 disks.  This port cannot reach that
  exact state - it has no filename-to-preference back-fill, so the "corrects only
  an empty value" half does not apply here - but it shares the half that matters
  to a user: romReleaseMismatchNotice states the bad pair and names no remedy.
  It should name the release the files on the device agree on, and offer it.
    One thing to check before writing any of this down as settled: contrary to
  what the surrounding code reads like, applyRomWBWVersionSwitch writes
  romwbwVersionKey UNCONDITIONALLY, automatic switches included, and
  romwbwVersionChosenKey is only ever set and never cleared - so "only a value
  the picker set is stored" is false, and any fix reasoning from it will be
  wrong.  Also: applyRomWBWVersionSwitch blanks selectedDisks in memory but the
  new release's slots are re-read later by restoreDiskSelections, off the back of
  fetchDiskCatalog, so a failed fetch leaves them un-re-read.


What a released build carries, and what the next one still owes
----------------------------------------------------------------------

- [RELEASE] v1.4.12 is what every installed copy still fetches from, so those
  tags must stay live:

    releaseTag WAS "v1.4.12" and an installed copy carries it at last - 0010591
    is an ancestor of build 61, which pins v1.4.12 outright.  Since 2026-09-04
    releases/latest IS v1.4.12 as well, so a device still floating on 1.4.9 gets
    the fixed R8 on a FRESH download - but start() only fetches a disk that is
    absent, so a 1.4.9 device already holding hd1k_combo.img keeps the old R8
    until it takes the 1.5.1 update.  On 1.5.1 the disk ledger is what replaces
    it, and the ledger has been driven on the simulator and never on a device.

    Build 64 deleted releaseTag: the tree now reads the romwbw_disks
    interface-v0 catalog and has no pin at all.  That changes nothing above -
    every installed copy still fetches from v1.4.12, those tags must stay live,
    and the fixed R8 still only reaches an installed device through a shipped
    build.  What it changes is the future: on a build-64 device the v0 catalog
    names hd1k_combo-v0-3.5.1.img and the disk ledger can refresh it unattended
    on Wi-Fi without an app release.

    DECIDED 2026-09-05, AND IMPLEMENTED: it does not refresh.  The migration
    renames rather than re-downloads, so a migrated device keeps its v1.4.12
    bytes under the v0 name - and hd1k_combo is the one image of twenty whose
    hash differs between the two catalogs: 89b8ae1a... at v1.4.12, 0ca4ec60...
    in romwbw_disks.  Both carry the same fixed r8.com and w8.com with the
    06 e9 cf HBF_HOST_CAPS probe; the bytes differ because romwbw_disks builds
    its own combo, not because anything is wrong with this one.  So the ledger's
    verdict is "superseded" on the strength of a hash that moved because the
    catalog moved, and acting on it spends 49 MB of a user's data for no
    functional change.  z80cpmw reaches the identical verdict and calls nothing
    that acts on it, which is the only reason it is harmless there.
    So CatalogMigration.equivalentPriorImage accepts that one prior image, and
    DiskLedger.freshness returns .current for it instead of .superseded.  It is
    keyed on PROVENANCE, which is what makes it safe: a download records the
    catalog it was fetched against, so only the migration can put the pre-v0
    hash there, and the exception stops applying the moment a device fetches the
    canonical image.  romwbw_disks' docs/FINDINGS.md section 10 has the byte
    ranges.

    DiskLedger.swift is what reaches those devices.  Driven end to end on the
    simulator against a real sandbox: a superseded image was measured, judged,
    replaced and recorded, and left alone on the next launch.

    emu_host_file_open_read() is synchronous, so R8 can report the file it is
    really reading.  Tests/CoreHostFileTests.cc drives the core sequence and
    run_tests.sh compiles the backend, but nothing has run it against a real

- [MAC] found by the build-67 audit and NOT fixed, in severity order.  Each was
  raised by a reviewer and survived three adversarial verifiers; each names a
  symbol rather than a line.  Four siblings of these WERE fixed in build 67 and
  are in the CHANGELOG, so this is the remainder, not the whole list.  Two more
  came off it on 2026-09-08 - waitForDownloadCompletion's endless poll and
  CatalogDocument.isPreview's docstring - and are in the CHANGELOG too.

  * loadCachedCatalog adopts a cached catalog with NONE of the parser's
    verification gates.  The cache lives in Documents/Disks, which is
    user-visible over iTunes file sharing and the Files app, so an edited
    catalog-v0-<rel>.json is trusted on the offline path where a fetched one
    would be rejected.  Verify the cache the way a download is verified, or say
    in the file why a cache is different.

  * applyRomWBWVersionSwitch blanks the four slots in memory and nothing
    restores them when the new release's catalog cannot be loaded, so the next
    slot edit persists four blanks over the saved configuration.  Reachable by
    switching release with no network.

  * start() has no re-entrancy guard and Play stays live through the whole
    ROM-and-disk download window, so a second press starts a second fetch/boot
    sequence over the first.

  * CatalogMigration.renames(in:) does not record a rename skipped because the
    destination already exists, so notMoved misses it and the stored names are
    rewritten to a file that was never created.  MANUAL_CHECKS 18's "a
    destination that already exists is kept" box covers the file half of this
    and passes; it is the KEY half that is wrong.

  * HelpView.fetchContent prefers the copy at releases/latest over the bundled
    one, and the served copy is still the pre-build-61 text - it tells iOS users
    to press Cmd+C.  Either upload the asset (docs/DISK_W8FIX_RUNBOOK.md governs
    it) or prefer the bundle when it is newer.

  * installedChecksumStatus(for:) paints the migrated combo's checksum red while
    the row correctly calls it up to date, because it does not consult
    CatalogMigration.isEquivalentPriorImage the way DiskLedger.freshness does.
    Cosmetic, and it contradicts the row beside it.

  * Tests/CatalogDocumentTests.swift asserts that an empty `keeping:` is treated
    as "no choice".  RomWBWIndex.preferred does not implement that - an empty
    string simply matches no release and falls through - so the test passes for
    a reason it does not state.

The index scoping of build 69 does not cover the install itself
----------------------------------------------------------------------

- [MAC] downloadDiskFromSettings writes a finished download to a LITERAL
  Documents/Disks, while every reader - isDiskDownloaded, downloadedDiskPath,
  refreshAvailableDisks, deleteDownloadedDisk, saveDownloadedDisks - goes through
  downloadsDirectory, which appends CatalogMigration.indexScope.  indexScope is
  empty for the built-in index, so nothing is wrong there and nothing shows; under
  a CUSTOM index the two disagree.  The download lands in the default library,
  refreshAvailableDisks then reports it as not downloaded, and it can overwrite a
  same-named image the user already had - which is the hazard build 69's own
  commit message says the scoping exists to prevent.
  The completion handler is the only place besides downloadsDirectory itself that
  builds this path by hand; grep the tree for the literal and there are two.
  Not run, only read: raised on 2026-09-13 from z80cpmw, while re-reading the
  ioscpm column of its FEATURE_PARITY.md.  Still present at build 72.  The
  simulator check that shipped with build 69 could not have caught it - it pointed
  at https://example.invalid, where no download ever completes.
