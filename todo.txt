  WordStar under Catalyst and walk the diamond: ^A ^D ^E ^F ^K ^P ^R ^S ^V ^X ^Y
  and ^QS. The analysis says AppKit's emacs StandardKeyBinding bindings cannot
  reach TerminalUIView - it is a plain UIView + UIKeyInput, not a UITextInput
  responder, and its own keyCommands sit on the first responder that UIKit
  consults first - and build 49 keeps the 26 Ctrl+letter UIKeyCommands
  specifically so that stays true. Confirm it. While there, confirm Escape still
  reaches the guest windowed and full-screen now that it sets
  wantsPriorityOverSystemBehavior (TerminalView.swift), and that it still
  dismisses an alert rather than being swallowed - keyCommands returns nil while
  captureKeyboard is false, and that flag now covers all three dialogs drawn
  over the terminal (disk-overwrite warning, error alert, reset confirmation),

  they cover the terminal and present their own responder. If a fourth dialog

- also unverifiable without a device: the reset confirmation
  (ContentView.swift). Built and reasoned about, never tapped.

- Ctrl+Left / Ctrl+Right / Ctrl+Up / Ctrl+Down still emit the same bytes as the
  plain arrows. The nav-key branch in pressesBegan tests only for .command, so
  the modifier is discarded before the Ctrl fold below it can see it. cpmemu's
  Windows platform layer does bind them (^A ^F ^W ^Z for word motion); z80cpmw
  does not. Small, and it needs a decision about which convention to follow
  rather than an implementation - written up in KNOWN_PROBLEMS.md.

- the parity items still genuinely absent, in rough order of how much they are
  missed. Each is a feature, not a sync gap - none block taking a core release.
  - no on-screen navigation/function key row, so the key map is unreachable on a
    touch-only device. This is now the largest gap: build 51 gave the map all 22
    keys including F1-F12, and on an iPhone or a keyboard-less iPad there is
    still no way to press any of them. cpmdroid's buildKeyRow (MainActivity.kt),
    backed by TerminalView.sendNamedKey, is the worked example, and
    SpecialKey.functionKeys exists to feed exactly this.
  - no configuration profiles - named sets of ROM, disks, boot string, terminal
    and key map. KeyProfile is only the key-map half.
  - no Catalyst window-state persistence and no Emulator menu. Note this row is
    NOT N/A the way it is for mobile: a Catalyst window is a resizable desktop
    window that opens at the system default every launch.

- the terminal's remaining divergence from a strict VT, now that build 51 added
  the editing finals: the erase family (ED, EL, ICH, DCH, ECH) blanks with a
  default cell rather than painting the current SGR background. A strict VT
  paints it. Changing that is a decision for the whole family at once - doing it
  to half would be worse than the current consistent-but-wrong behaviour.

- the terminal parser has no unit tests, and build 51's editing finals were
  verified by building and by reading, not by running. The obstacle is that the
  parser lives in EmulatorViewModel, which is UIKit-bound; TerminalDialect,
  ControlKey and KeyMap were each split out precisely so they could be tested,
  and the screen model is the next candidate. It is a bigger extraction than
  those three - it owns terminalCells, the cursor, the scrolling region and
  scrollback - which is why it has not been done rather than that it should not
  be.

- release chore, not code: release_assets/help_quick_start.md was corrected in
  build 49 (it advertised a Ctrl+E emulator console that does not exist, which
  is actively harmful because ^E is WordStar cursor-up). Build 51 bundles the
  corrected copy into the app, so an offline user and a user hitting a 404 both
  get the right text now - but the download still takes priority when it
  succeeds, which is deliberate, so a user WITH a network still sees the stale
  published copy until the file is re-attached to the newest release. Less
  harmful, not fixed.

- reminder before touching anything under iOSCPM/Core/ from a windows machine:
  read docs/notes_to_windos.md. All 21 of those are symlinks into ../romwbw_emu
  and ../cpmemu and have been flattened once already. The manual check that used
  to be written here - `git ls-files -s iOSCPM/Core/ | grep ^120000`, expecting
  21 - is automated since build 50: Tests/run_tests.sh runs it first and fails
  if the count is wrong or a link dangles.

  The sharper hazard that doc records is not automated and cannot be: the
  symlinks resolve into sibling *working trees*, so this port compiles whatever
  branch those repos happen to have checked out, and a test that proves the
  links are links cannot prove the trees behind them are on the right branch.
  As of build 50, ../cpmemu is on branch posix-console rather than main. It is
  harmless - that branch is one commit ahead and touches no qkz80 file - but
  nothing enforces it.
