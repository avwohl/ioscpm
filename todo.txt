Release
-------

- [RELEASE] do not bump releaseTag (grep releaseTag in EmulatorViewModel.swift,
  still v1.4.5) until build 52 or later is what users are running.  Refreshing
  the disk-image catalog is what puts a path-capable W8 in front of everyone.
  The cross-repo order is romwbw_emu docs/RELEASE_ORDER_2026-08-25.md; this port
  is step 1 and the catalog pin bump is step 5.  The one thing that must never
  happen is refreshed images attached to the EXISTING v1.4.5 tag - that reaches
  every installed app with no update at all.  Read the next item before walking
  that order.

- [DECISION] the catalog bump wipes disks the catalog cannot give back, and
  nothing decides what should happen instead.  checkCatalogVersionAndInvalidate
  compares disks.xml's version attribute against the stored catalogVersion
  default and calls deleteAllDownloadedDisks() on any difference; that loop
  takes every .img in Documents/Disks, including ones the user imported through
  Files and ones createNewDisk made in the app.  Nothing fires today - both
  sides are at 13 - and the release step that bumps the attribute fires it on
  every installed device at once, unprompted.  The options are copy-on-write on
  first guest write, confirm before wiping, spare anything the catalog does not
  name, or keep the wipe behind an export path first.  Whichever it is has to
  ship in the same binary as the pin bump, for the same reason build 52 does.
  Mechanism written up under "Data Loss Risk with GitHub Disks" in
  KNOWN_PROBLEMS.md.

- [RELEASE] two published help files are behind and need someone who can attach
  assets to a GitHub release.  Help does not follow the pin: HelpView.swift
  hardcodes releases/latest, and releaseTag feeds the disk catalog only, so
  Latest - v1.4.11 - is what to re-attach to.  help_quick_start.md still says
  "Press Ctrl+E to access the emulator console"; there is no console and ^E is
  WordStar cursor-up.  help_file_transfer.md names the wrong app and bundle id
  ("Files app -> iOSCPM", com.awohl.iOSCPM; both are Z80CPM / com.awohl.cpm now)
  and predates "Import File... (for R8)".  The corrected text is in
  release_assets/ and ships inside the app, so only a networked user gets the
  stale copy.  The other five topics and help_index.json are already identical
  and need nothing.


Needs a Mac
-----------

- [MAC] emu_host_file_get_read_name() answers "" and could answer truthfully.
  "" is legal - emu_io.h says so, HBF_HOST_GETRNAME reports "no answer" and R8
  falls back to printing what was asked for - but the Swift layer resolves the
  guest's leaf against Imports case-insensitively, so R8 FOO.COM that really
  opened foo.com reports FOO.COM.  The resolved name never crosses back into the
  backend: emu_host_file_load(), the extern "C" entry point Swift calls, carries
  bytes and no name.  Shape of the fix: a named variant of that entry point
  storing the path in a g_host_read_filename that the getter returns while
  HOST_FILE_READING, exactly as the write side already does with
  g_host_write_filename.  romwbw_emu's browser backend answers "" for the same
  reason and has the same item open.

- [MAC] nothing verifies a downloaded disk's SHA256.  downloadDiskWithRetry()
  does hash, delete and retry on a mismatch, but its only callers are its own
  four retry arms, so nothing outside it reaches it.  Every real download goes
  through downloadDiskFromSettings() - both downloadDisk() and
  downloadDiskWithCompletion() call it - and that one moves the temp file into
  place without hashing.  The catalog's sha256 survives only as the coloured
  text in DiskDownloadRow, computed after the file is installed and acted on by
  nobody.  Disk images are downloaded content the guest then executes, so this
  matters most on exactly the release step above.  Either delete the dead path
  or move its check into the live one.  DISK_DISTRIBUTION.md's "Integrity
  Verification" section is labelled intended-not-shipped; that label comes off
  when this closes.

- [MAC] new disks are always 8 MB and the size is hardcoded twice.
  createNewDisk(at:size:) takes a size: its single ContentView call site does
  not pass, and the .fileExporter that runs first hands it EmptyDiskDocument,
  whose fileWrapper writes its own Data(repeating: 0xE5, count: 8 * 1024 * 1024)
  without consulting defaultDiskSize.  A size picker has to feed both or the
  exporter lays down 8 MB and only the rewrite honours the choice.  Imported
  disks are already accepted up to maxDiskSize (64 MB).  A created disk is 0xE5
  fill and no filesystem, which is what the cpmtools recipe in KNOWN_PROBLEMS.md
  works around.

- [MAC] the CSI parser has no unit tests.  executeCSI (EmulatorViewModel.swift,
  ~280 lines) is verified by reading and by building only - build 51's editing
  finals and build 53's 17-site erase sweep included, and that sweep is exactly
  what a test would have checked in a second.  The five suites in Tests/ cover
  TerminalDialect, ControlKey, KeyMap, ExportPath and the C++ core keyboard;
  each of the four Swift ones was split out of a view precisely so it could be
  tested, and the screen model - terminalCells, the cursor, the scrolling
  region, scrollback - is the next and biggest such extraction.  Copy z80cpmw's
  tests/: bytes in through the public write path, screen out through the public
  accessor, cursor through ESC [ 6 n.  Its tests/test_vt52.cpp already asserts
  the erase cases.

- [MAC] parity gaps, in rough order of how much they are missed.  Each is a
  feature, not a sync gap - none blocks taking a core release.
  - no on-screen navigation/function key row, so on an iPhone or a
    keyboard-less iPad none of the map's 22 keys can be pressed at all.  Largest
    gap, and build 51 widened it by adding twelve more.  The toolbar in
    TerminalWithToolbar (TerminalView.swift) is Ctrl, Esc, Tab and a Spacer and
    is the place to grow one; SpecialKey.functionKeys exists to feed it.  No
    worked example in the family to copy - z80cpmw's FEATURE_PARITY.md says the
    same.
  - no configuration profiles - named sets of ROM, disks, boot string, terminal
    and key map.  KeyProfile (KeyMap.swift) is only the key-map half.
  - no Catalyst window-state persistence and no Emulator menu; iOSCPMApp.swift
    replaces only CommandGroup(.help).  Not N/A the way it is for mobile: a
    Catalyst window is a resizable desktop window that opens at the system
    default every launch.


Cross-port decision
-------------------

- [DECISION] SGR colour indices are ANSI numbers stored in a CGA-ordered byte,
  so four of the eight come out wrong.  applySGR stores the raw ANSI index -
  (currentAttr & 0xF0) | (param - 30) for 30..37, (param - 40) << 4 for 40..47 -
  and TerminalView's cgaColors is a CGA palette.  ANSI is black red green yellow
  blue magenta cyan white; CGA is black blue green cyan red magenta brown
  lightgray, so 1 and 4 swap and 3 and 6 swap: ESC[31m draws blue, ESC[34m draws
  red, ESC[33m draws cyan, ESC[36m draws brown.  Seen on the simulator
  2026-08-27, where ESC[44m ESC[2J filled the screen solid red.  NOT a
  divergence: z80cpmw does the identical thing (applySGR stores param-30 /
  param-40, cgaToRGB is the same table), so fixing it here alone would break the
  one thing the ports agree on.  Three lines of lookup table on each side, and a
  decision for whoever owns all three.  The VDA path must stay as it is - HBIOS
  really does hand over CGA attribute bytes and emulatorVDASetAttr is right to
  take them raw.  Only the SGR entry points are wrong.
