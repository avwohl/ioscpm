FETCH THE ROM FROM THE CATALOG - THE LAST VERSION-COUPLED THING IN THIS APP
-------------------------------------------------------------------------------

- [ANY] this app bundles a 3.5.1 ROM (iOSCPM/Resources/emu_avw.rom, via
availableROMs/bundledROMFilename) and downloads no ROM at all.
  romwbw_disks published RomWBW 3.6.0 as stable and
default on 2026-09-05, so a build shipped as it stands would preselect 3.6.0
disks and boot them against a 3.5.1 ROM -> *** WARNING: HBIOS/CBIOS Version
Mismatch ***.  Nothing is broken today: no released build reads that index, and a
pre-v1.39 core filters 3.6.0 out by hbios.ver_byte before default is ever read.
  The fix is to fetch the ROM from the catalog the way disks are fetched.  It is
NOT to bundle a 3.6.0 ROM instead: that would put a store release for this app on
the critical path for every RomWBW version, which is the whole cost romwbw_disks
was created to remove.  Every catalog already carries roms[] with emu_avw flagged
default, a sha256 and a size, under the same base_url as the disks.
  Most of it already exists here.  CatalogDocument decodes roms[] as romEntries
and defaultROM and correctly does not assume emu_avw is present, and the bridge
exposes loadROMFromPath: and loadROMFromData: already on the live path
(loadROM(fromBundle:) reaches them).  What is missing is the caller that hands
them a DOWNLOADED path.  Keep the bundled ROM as the first-launch fallback:
docs/ROM_ATTESTATION.md is an App Store filing naming emu_avw.rom as a reviewed
asset, and the app should boot offline out of the box.
  romwbw_disks/docs/ROMWBW_VERSIONS.md "Why 3.6.0 is stable and default" has the
same gate written down at the publishing end.

    DECIDED 2026-09-05, AND IMPLEMENTED: it does not refresh.  The migration
    renames rather than re-downloads, so a migrated device keeps its v1.4.12
    bytes under the v0 name - and hd1k_combo is the one image of twenty whose
    hash differs between the two catalogs: 89b8ae1a... at v1.4.12, 0ca4ec60...
    in romwbw_disks.  Both carry the same fixed r8.com and w8.com with the
    06 e9 cf HBF_HOST_CAPS probe; the bytes differ because romwbw_disks builds
    its own combo, not because anything is wrong with this one.  So the ledger's
    verdict is "superseded" on the strength of a hash that moved because the
    catalog moved, and acting on it spends 49 MB of a user's data for no
    functional change.  z80cpmw reaches the identical verdict and calls nothing
    that acts on it, which is the only reason it is harmless there.
    So CatalogMigration.equivalentPriorImage accepts that one prior image, and
    DiskLedger.freshness returns .current for it instead of .superseded.  It is
    keyed on PROVENANCE, which is what makes it safe: a download records the
    catalog it was fetched against, so only the migration can put the pre-v0
    hash there, and the exception stops applying the moment a device fetches the
    canonical image.  romwbw_disks' docs/FINDINGS.md section 10 has the byte
    ranges.

    DiskLedger.swift is what reaches those devices.  Driven end to end on the
    simulator against a real sandbox: a superseded image was measured, judged,
    replaced and recorded, and left alone on the next launch.

  shape actually comes up as several drive letters, or whether it needs the hd1k
  shape with a hand-written type-0x2E MBR.  Both readings agree on what
  emu_check_disk_size() accepts and disagree about what HBF_EXTSLICE does with a
  0xE5 image over 8 MB.  WIP.md carries the argument on both sides and the reason
  the current code is believed right; MANUAL_CHECKS.md section 12 is the check
  that answers it.
